# 首条回复与连续消息处理

2026-10-23。已实现并更新安装目录中的后台聊天引擎。

## 用户看到的行为

| 情况 | 处理 |
| --- | --- |
| 会话空闲，收到第一条消息 | 立即开始处理，不先等待合并窗口。 |
| 同一人还在补充，上一轮尚未尝试发送 | 取消旧生成，把原问题与补充按顺序合并，统一回答。 |
| 同一人补充时，已有内容发送或正在等发送回执 | 保留已发内容，等待在途发送确定结果，停止旧回复的其余气泡，处理补充。 |
| 补充连着到达 | 待处理补充使用 300ms 收拢窗口；单个待处理批次最多等待 1200ms，最多八条、合计 6000 字。超出后另排一轮。 |
| 同一群里的不同成员提问 | 分别保留提问者与引用对象，按到达顺序处理，不合并不同人的问题。 |
| 其他群、私聊、QQ 账号或人格 | 使用独立会话队列。 |
| 斜杠命令、工具操作 | 斜杠命令保持逐项处理；工具执行期间不因聊天补充而取消、重跑动作。 |
| 等待旧语音生成时收到新消息 | 停止等待旧语音，处理新消息；已在途的合成可能完成，但旧音频不会再发送。 |

群内沿用明确 @ 机器人才响应的规则，补充消息也需要 @。只在一轮首条发送中引用、@ 对方。重复 OneBot 事件仍按消息编号去重。待处理队列最多八轮，满时在队列中给出一次提示，避免提示与正常回答穿插。

## 首条为什么能提前

`askAI` 在自然聊天提供增量回调时使用 Chat Completions SSE。解码器跨网络分片保留 UTF-8 字节、SSE 行及帧边界，只读取 `delta.content`；推理内容、工具参数和原始服务诊断不会进入 QQ。

只有标准顺序的 version=2 信封中，第一个完整的 text 项可提前投递。该项必须完成 JSON 解码、正文检查及单项协议校验。不会发半句话、JSON 原文或媒体占位符。其余项继续等待完整计划校验；图片与语音保持原有本地素材和声音权限限制。若后半段损坏，保留已投递正文，停止后续，不重发正文或整轮重试。

不提供增量的后端继续等完整生成，但合法 version=2 计划的首条文字可在图片准备前投递。显式要求互补语音时，先完成文字与语音去重，防止提前发送后来应移入语音的重复正文。

群成员名单刷新最多等待 150ms，之后用现有成员与当前消息信息继续，刷新仍可在后台完成。作业、记忆、历史摘要和可用素材列表并行读取。

| 同一次请求中的时刻 | 耗时 |

| 完整回答生成结束 | 8266ms |

这是一条真实请求的观测，不能视为长期平均或手机端到达时间。生成长短、网络与服务负载会影响结果。
